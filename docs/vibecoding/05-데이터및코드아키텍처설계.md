# 5. 데이터 설계 & 코드 아키텍처 설계 — Peekpop

작성일: 2026-08-29
상태: 완료

원칙: 로그인·서버가 없는 온디바이스 서비스이고, "최대한 간결하고 빠르게 출시"가 팀 가치관이므로 불필요한 추상화·인프라를 만들지 않는다.

## 데이터 설계

서버/DB가 없으므로 영속 데이터는 사실상 없다. 로컬에 남는 건 두 개뿐이다.

| 키 | 타입 | 저장 방식 | 용도 |
|---|---|---|---|
| `hasSeenOnboarding` | Bool | `@AppStorage` | 최초 실행 여부 판단, 이후 온보딩 스킵 |
| `lastFreeUseDate` | Date? | `@AppStorage` | (다음 버전용) "하루 1회 무료" 로직 — MVP에서는 미사용, 필드만 예약 |

- 사진 자체는 앱이 저장하지 않는다 — 파이프라인이 도는 동안만 메모리(`UIImage`/`CGImage`)에 있다가, 결과물만 `PhotosUI`로 카메라롤에 저장한다.
- Core Data/SwiftData 등 DB는 필요 없다.

## 코드 아키텍처

단일 Xcode 프로젝트, 단일 앱 타겟. 모듈 분리(SPM 패키지 등)는 이 규모에서 과함 — 하지 않는다.

### 레이어 구성

```
Views/           SwiftUI 뷰, 화면당 하나 (OnboardingView, MainView, BoundaryConfirmView,
                  BrushRefineView, ResultView, LoadingView, ErrorView 등)
Flow/             CreationFlowViewModel — 흐름 전체의 상태를 들고 있는 단일 ObservableObject
Services/         PhoneFrameDetector, SubjectSegmenter, PopOutCompositor — Vision/CoreGraphics 래퍼
```

- **Views**: [[04-화면설계]]의 화면 8개에 1:1 대응. 상태를 직접 들지 않고 `CreationFlowViewModel`을 관찰만 한다.
- **CreationFlowViewModel**: 선택된 사진, 확정된 화면 사각형(4점), AI/브러시 마스크, 합성 결과, 현재 화면(enum), 에러 상태를 전부 들고 있는 단일 소스. 화면이 늘어난다고 ViewModel을 화면별로 쪼개지 않는다 — 흐름이 선형이라 하나로 충분하고, 쪼개면 상태 동기화 비용만 늘어난다.
- **Services**: [[02-기술스택선정]]에서 정한 3개 그대로 — 프로토콜 추상화 없이 concrete 타입으로 둔다 (테스트는 실제 샘플 이미지로 돌릴 거라 Vision을 mock할 이유가 없음 — YAGNI).

### 화면 전환

`enum Screen { case onboarding(page: Int), main, boundaryConfirm, generating, brushRefine, compositing, result, error(String) }` 를 `CreationFlowViewModel`이 들고, 루트 뷰가 이 값으로 switch해서 화면을 바꾼다. `NavigationStack`은 쓰지 않는다 — "다시 만들기"처럼 스택을 여러 단계 건너뛰는 이동이 있어서, push/pop보다 상태값 하나로 화면을 바꾸는 쪽이 더 간결하다.

### 동시성

Vision 처리(화면 인식, 마스크 생성)는 Swift Concurrency(`async`/`await`)로 감싼다. `VNImageRequestHandler.perform`은 동기 API라 `Task { }` 블록 안에서 실행하고, 완료되면 메인 액터에서 `CreationFlowViewModel` 상태를 갱신한다.

### 합성 배치 로직 (기울기 반영)

[[01-구현가능성검증]]에서 확인했듯, 컷아웃 배치는 사용자가 지정한 화면 사각형의 기울기를 반영해야 자연스럽다. `PopOutCompositor`는:
1. 사용자가 지정한 4점에서 사각형의 회전각을 계산한다 (예: 아래쪽 두 점을 잇는 선의 기울기).
2. 컷아웃 이미지를 그 각도만큼 회전시킨 뒤, 사각형의 아래쪽 변 바깥으로 일부 걸치도록 배치한다.
3. 그림자는 회전된 배치 방향에 맞춰 오프셋을 준다.

정확한 배치 비율(확대 배율, 얼마나 걸치게 할지)은 스파이크에서 고정값으로 대략 검증한 수준이라, 실제 구현 중 여러 샘플로 미세 조정이 필요하다 (이미 [[01-구현가능성검증]]에 기록됨).

### 에러 처리 흐름

Vision 단계에서 실제 예외(인식 실패가 아닌 진짜 오류)가 발생하면 `CreationFlowViewModel`이 이를 캐치해 `Screen.error(message)`로 전환한다. [[04-화면설계]]의 에러 화면과 동일한 패턴 — "다시 시도" 버튼 하나로 사진 선택 화면으로 복귀.

### 테스트 범위

"간결하고 빠르게" 원칙에 따라 자동화 테스트는 최소로 한다.

- 유닛 테스트 대상: `PhoneFrameDetector`, `SubjectSegmenter`, `PopOutCompositor` — 번들에 포함한 샘플 이미지 몇 장으로 회귀 테스트만 둔다.
- SwiftUI 뷰/화면 흐름에 대한 UI 테스트는 만들지 않는다 — [[01-구현가능성검증]]에서 이미 수행한 실기기 수동 QA로 대신한다.
