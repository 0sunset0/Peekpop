# ADE (기술적 결정사항) — Peekpop

각 항목은 "무엇을 왜" 형식의 결정 기록. 재논의 없이 참고만 하면 된다.

## 화면 경계 인식: 자동 결과를 신뢰하지 않고 프리필+사용자 확인으로
`VNDetectRectanglesRequest`를 실제 후보 사진 4장에 테스트 — 정확 검출 25%, **신뢰도 1.00으로 확신에 찬 오탐 50%**, 미검출 25%. 오탐이 가장 위험한 이유는 사용자가 원인도 모른 채 이상한 결과를 받기 때문. → 자동 결과는 초안(프리필) 용도로만 쓰고, 사용자가 4꼭짓점을 항상 확인/조정한다.

## 인물 추출: "사람" 카테고리 인식기 배제, 크롭 후 범용 전경 인식 채택
`VNGeneratePersonSegmentationRequest`/`VNGeneratePersonInstanceMaskRequest`는 가장 깔끔한 샘플에서도 0% 인식됐다 — 화면에 "찍힌 사진 속 인물"이라 실물 사람과 다르게 인식되는 것으로 판단. 대신 `VNGenerateForegroundInstanceMaskRequest`(iOS "피사체 들어올리기"와 동일 계열, 클래스 불특정)를 **사용자가 확정한 영역으로 크롭한 이미지에만** 실행하면 안정적이었다(25~56% 커버리지, 깨끗한 실루엣). 원본 전체 사진에 바로 실행하면 신뢰도가 급락한다.

## 크롭 대상: 폰 UI 제외, "사진 부분만"
카메라 앱 UI(상태바, 촬영 버튼 등)까지 포함해서 크롭하면, AI가 인물이 아니라 "UI 대비 밝은 사각형 사진 영역 전체"를 하나의 덩어리로 오려낸다 — 합성 결과가 인물이 아니라 폰이 하나 더 겹친 것처럼 보인다. UI를 제외하고 사진이 실제로 표시되는 부분만 크롭하면 인물 실루엣이 머리카락/옷 주름까지 깨끗하게 분리된다.

## 합성 배치: 사각형 기울기 반영 필수
고정 비율로 확대·배치하면 폰이 수직에 가까운 사진에서만 자연스럽고, 기울어진 사진에서는 어색하다. 사용자가 지정한 4점에 이미 기울기 정보가 있으므로, 그 각도로 컷아웃을 회전시켜 배치한다 (구현은 code-architecture.md). AI 인식의 한계가 아니라 기하학 계산으로 풀리는 문제.

## 외부 AI API(Claude 등) 미채택
정밀 픽셀 마스크 생성 용도에 부적합하고, 네트워크 필수·API 비용 발생이 무계정·온디바이스 서비스 방향과 상충한다. 온디바이스 Vision 프레임워크만으로 전체 파이프라인이 기술적으로 가능함을 확인했다.

## NavigationStack 대신 enum 기반 화면 전환
"홈으로"/"다시 시도"처럼 스택 여러 단계를 건너뛰는 이동이 있어, push/pop 스택보다 단일 상태값 switch가 더 간결하다. ("최대한 간결하고 빠르게" 원칙)

## 결과 화면 "홈으로" vs 뒤로가기/재시도의 피커 자동 표시 차이 (2026-08-29)
초기엔 "다시 만들기"가 `startOver()`(메인 전환 + 피커 자동 오픈)를 그대로 썼다. 사용자가 라벨을 "홈으로"로 바꾸면서 동작도 "메인 화면에 머무르고, 사용자가 직접 사진 선택하기를 눌러야 피커가 뜨게" 바꿔달라고 요청 — 라벨이 "홈"을 말하면 사용자는 정적인 화면에 도착할 거라 기대하는데, 곧장 피커가 뜨면 라벨-행동 불일치가 생기기 때문. `CreationFlowViewModel.goHome()`을 별도로 추가해 `isPickerPresented`를 건드리지 않게 했다. 경계확인 화면의 뒤로가기(`<`)와 에러 화면의 "다시 시도"는 `flow.md`상 "2(사진 선택)로 복귀"가 명세라 기존 `startOver()`/`retryFromError()`(피커 자동 오픈) 그대로 유지 — 셋 다 "돌아가기" 계열이지만 목적지가 다르므로 함수를 통일하지 않았다.

## 타이포 위계 3단 정리 (디자인 리뷰, 2026-08-29)
안내 문구·버튼 라벨·보조 힌트가 전부 `.body` 근처 크기/굵기로 시각적 구분이 없다는 지적을 받아, 화면당 "지금 뭘 해야 하는지" 알려주는 안내 문구는 `.title3.weight(.semibold)`로 올리고, 결과 화면의 조작 힌트·"홈으로" 링크 같은 보조 텍스트는 `.footnote` + 흰색 60% 투명도로 낮췄다. 버튼 라벨(`PrimaryButtonStyle`의 `.headline`)은 그대로 유지 — 이미 굵기로 구분되고 있었다. 포인트 컬러(무채색 탈피)는 사용자가 직접 고르기로 하고 이번 변경에 포함하지 않았다.

## 배경색: 순정 검정 유지 결정 (디자인 리뷰, 2026-08-29)
"다크모드=순정 검정"이 관례가 아니라는 지적(Material Design은 `#121212`, Apple도 그룹형 화면엔 `#1C1C1E` 근처를 씀 — OLED halation과 elevation 표현력 문제 때문)이 나왔지만, Peekpop은 모든 화면이 사진 하나가 꽉 채우는 몰입형 뷰어(카메라·사진 앱의 전체화면 뷰어와 동일 패턴)이고 "꺼진 폰 화면에서 튀어나온다"는 컨셉과도 맞아 순정 검정(`#000000`)을 그대로 유지하기로 했다. 다만 배경과 거의 안 구분되던 결과 화면 토스트만 표면색(`#1C1C1E`, `Color.peekpopSurface`)으로 바꿨다.

## 포인트 컬러: 코랄 `#FF5C7A` (디자인 리뷰, 2026-08-29)
순정 검정 배경 위에서 색이 발광하듯 보이는 효과를 고려해 후보 3개(코랄/바이올렛/블루)를 제시했고, 사용자가 코랄 `#FF5C7A`로 결정했다. `Color.peekpopAccent`(`Peekpop/Shared/AppColor.swift`)로 정의하고 Primary 버튼 배경(`PrimaryButtonStyle`)과 처리중 화면 스피너 tint에만 적용 — Share/홈으로 같은 보조 액션은 의도적으로 무채색 유지(색을 아껴야 "메인 액션" 위계 신호가 유지됨). 버튼 라벨 텍스트는 기존처럼 검정 유지(흰 글자 대비 대비비가 약 2.97:1로 WCAG 기준 미달, 검정 글자는 약 7:1로 충분).

## 경계 확인 화면 뒤로가기 버튼 가시성 (디자인 리뷰, 2026-08-29)
흰 chevron 아이콘만 있어서, 사용자가 업로드한 사진의 밝은 영역과 겹치면 잘 안 보인다는 문제가 있었다. 1차로 반투명 검정 스크림(`Color.black.opacity(0.45)`)을 넣었지만 여전히 잘 안 보인다는 재지적을 받아 완전 불투명 `Color.peekpopSurface`로 바꿨는데, 이번엔 "너무 불투명하다"는 반대 방향 피드백을 받았다. 최종적으로 `Color.peekpopSurface.opacity(0.6)`로 정착 — 순정 흰색 사진 배경 위에 놓여도 대비비가 약 4.5:1(아이콘 기준 WCAG 최소 3:1을 넉넉히 상회)이라 항상 읽히면서도, 완전 불투명보다는 사진이 은은하게 비쳐 덜 무거워 보인다.

## 메인 화면 사진 선택 팝업이 엉뚱한 위치에 뜨는 문제 (실기기 QA, 2026-08-29, iOS 26)
사용자가 "카메라로 촬영/앨범에서 선택" 팝업이 예시 사진 위에 겹쳐서 이상하게 뜬다고 지적. 처음엔 "iOS 표준 액션시트는 하단에서 슬라이드로 올라온다"고 잘못 답했는데, 실기기 스크린샷을 받아보니 전혀 다른 모습이었다 — 화면 상단, 예시 사진 바로 위에 꼬리 달린 말풍선(팝오버) 형태로 떴고, 그 꼬리도 "사진 선택하기" 버튼이 아니라 사진 쪽을 가리키고 있었다.

원인: `.confirmationDialog(...)`가 "사진 선택하기" `Button`이 아니라 그 바깥의 전체 화면 `VStack`에 붙어 있었다. iOS 26의 Liquid Glass 디자인에서 confirmationDialog가 앵커 팝오버 형태로 뜨는데(과거의 항상-하단-시트 방식과 다름), 앵커 기준은 "modifier가 붙은 뷰"라서 화면 전체 VStack에 붙이면 그 뷰의 (엉뚱한) 위치를 기준으로 팝업이 뜬다. `.confirmationDialog`를 "사진 선택하기" `Button` 자체로 옮겨서 팝업이 그 버튼을 기준으로 뜨도록 수정 — 실기기 재확인 필요(SwiftUI 코드 레벨에서는 앵커가 버튼으로 바뀌는 게 맞지만, 팝오버가 실제로 버튼 근처에 뜨는지는 사용자 확인 대기 중).

## 경계확인 화면 레이아웃 분리 + 사각형 좌표 버그 발견/수정 (디자인 리뷰, 2026-08-29)
사용자가 "사진과 텍스트 박스가 겹치지 않았으면 좋겠다"고 제안 — 사진(+사각형 조정 영역) / 안내 카드 / 확인 버튼을 세로로 분리하는 레이아웃으로 바꿨다.

이 작업 중 별개의 실제 버그를 발견했다: `Image(...).scaledToFit().frame(width: geo.size.width, height: geo.size.height)`는 사진 비율이 화면 비율과 다르면 레터박싱(위아래 또는 좌우 여백)이 생기는데, 기존 `QuadOverlay`는 `canvasSize: geo.size`(레터박싱 포함 전체 프레임)를 정규화 좌표의 기준으로 썼다. 반면 실제 크롭(`PopOutCompositor.boundingRect`)은 그 정규화 좌표를 이미지 자체의 픽셀 크기에 직접 적용한다 — 즉 사용자가 "화면 위 어디"에 맞췄는지와 "이미지 안 어디"로 해석되는지가, 레터박싱이 있는 사진(거의 모든 사진 — 화면 비율과 정확히 같은 사진은 드묾)에서는 서로 어긋나 있었다. `ResultView`는 같은 이슈가 없었다 — 제스처를 절대 위치(`value.location`)가 아니라 상대 이동량(`value.translation`)으로 처리해서 레터박싱 오프셋의 영향을 안 받았기 때문.

`ImageLayout.displayedRect(containerSize:imageSize:)`(`Peekpop/Shared/ImageLayout.swift`)를 새로 만들어 실제 레터박싱된 이미지 영역을 계산하고, `QuadOverlay`가 이 사각형을 기준으로 좌표를 변환하도록 고쳤다. `ResultView`의 기존 `displayedSize` 계산도 같은 로직이라 중복을 없애고 이 함수를 재사용하도록 리팩터링했다. 유닛 테스트 3케이스 추가.

## 안내 문구 크기: title3 → 표준 본문(.body) (디자인 리뷰, 2026-08-29)
`.medium`으로 낮춘 뒤에도 "폰 화면 테두리에 맞춰주세요" 같은 문장이 여전히 크게 느껴진다는 피드백 — "정해진 본문 글씨 크기였으면 좋겠다"는 구체적 요청으로, 커스텀 크기(title3, 20pt) 대신 iOS 표준 `.body`(17pt regular)로 낮췄다. 전 화면(메인·경계확인·처리중·에러) 일괄 적용. 버튼 라벨(`.headline`, 17pt semibold)과는 이제 크기가 아니라 굵기 차이로 구분된다 — title3 단계에서 지키려던 "크기로 위계를 준다"는 원칙은 폐기되고, 대신 표준 타입 스케일을 따르는 쪽을 선택했다.

## 안내 문구 타이포/카드 배경 재조정 (디자인 리뷰, 2026-08-29)
경계확인 화면의 새 안내 문구가 "너무 두껍고 행간이 좁다", 카드 배경이 "너무 불투명하다"는 지적을 받고 냉정하게 재검토했다. 동의한 부분: 안내 문구 타이포(1단)를 `.title3.weight(.semibold)`로 정한 건 짧은 라벨성 문구엔 괜찮지만, 온전한 문장 길이의 텍스트에는 두껍게 느껴진다 — 실제로 버튼 라벨(`.headline`)과의 위계 구분은 애초에 크기(20pt vs 17pt) 차이만으로 충분했고 굵기까지 세게 갈 필요는 없었다. `.medium`으로 낮추고 `lineSpacing(4)`를 추가해 전 화면(메인·경계확인·처리중·에러) 안내 문구에 일괄 적용했다. 카드 배경은 완전 불투명 `peekpopSurface` 대신 `.opacity(0.85)`로 — 순백 배경 위에서도 대비가 충분히 유지되는 선(뒤로가기 버튼의 60%보다 훨씬 안전한 마진)을 확인하고 낮췄다.

## 경계확인 안내 문구 재작성 + 카드 배경 (디자인 리뷰, 2026-08-29)
기존 문구("화면에 보이는 사진이 네 꼭짓점 안에 전부 들어오도록 맞춰주세요 (머리 위쪽까지!)")는 두 가지 문제가 있었다: 1) "꼭짓점"이 일반 사용자에게 기하학 용어라 화면에 보이는 "노란 점"과 괴리가 있었고, 2) "(머리 위쪽까지!)"는 나중에 발견한 크롭 버그를 급하게 괄호로 덧붙인 것이라 톤이 안 맞았다. 사용자가 실기기 QA 중 "핸드폰 꼭짓점(=폰 화면 테두리)에 맞추면 인식이 더 잘된다"는 인사이트를 줘서, 문구를 "노란 점을 움직여서 폰 화면 테두리에 맞춰주세요"로 재작성 — 기하학 용어 없이 사용자가 실제로 보는 대상(폰 화면) 기준으로 안내한다. 폰 화면 테두리에 정확히 맞추도록 유도하면 "머리 위쪽이 잘리는" 문제도 부작용으로 해결되므로 별도 패치 문구가 필요 없어졌다. 동시에 텍스트를 표면색(`peekpopSurface`) 카드로 감싸 사진 밝기와 무관하게 항상 잘 읽히게 했다(뒤로가기 버튼 가시성 수정과 같은 원리).

## 결과 화면에 경계확인 화면으로 돌아가는 "<" 버튼 추가 (디자인 리뷰, 2026-08-29)
결과가 마음에 안 드는 흔한 이유는 "사진을 잘못 골라서"보다 "경계 사각형을 좀 잘못 맞춰서"인 경우가 많다는 논의에서 나왔다 — 예컨대 앞서 미뤄둔 "피사체 머리가 잘리는" 문제도, 사용자가 사각형을 더 넉넉하게 다시 맞추면 알고리즘 수정 없이도 스스로 우회할 수 있다. 기존엔 결과 화면에서 나가는 방법이 X(홈으로, `selectedImage`까지 초기화)뿐이라, 사각형만 다시 맞추고 싶어도 앨범에서 같은 사진을 처음부터 재선택해야 했다. `CreationFlowViewModel.backToBoundaryConfirm()`을 추가해 `selectedImage`와 마지막으로 확정한 `quad`는 유지한 채 경계확인 화면으로 돌아가게 했다(`resultImage`/`maskedCutout`/조정값만 리셋). 결과 화면 좌상단에 배치해 우상단 X와 역할을 분명히 나눴다: "<" = 이 사진으로 사각형만 다시, X = 사진부터 완전히 새로.

## 결과 화면 "홈으로" 텍스트 링크 → 우측 상단 X 버튼 (디자인 리뷰, 2026-08-29)
사용자 제안으로 바꿨다. 근거: 1) 결과 확인 후 나가는 화면에서 우상단 X는 스냅챗/인스타 스토리/애플 사진 마크업 등에서 흔히 쓰는 표준 패턴이라 별도 학습 없이 이해됨, 2) 하단에 있던 "홈으로" 링크를 치우면 하단이 순수하게 "이 사진으로 뭘 할지"(저장/공유)에만 집중돼 저장 버튼 존재감이 커짐, 3) 경계확인 화면 좌상단 뒤로가기(`<`)와 짝을 이뤄 "위쪽 모서리 = 화면 이동/나가기" 문법이 앱 전체에서 일관됨. X를 "취소/닫기"로 오해해 저장한 내용이 사라지는 줄 착각할 수 있다는 우려도 있었지만, 저장은 별도 버튼으로 이미 완료되므로 실질적 문제는 없다고 판단. `CreationFlowViewModel.goHome()`은 그대로 재사용(호출 지점만 바뀜), 뒤로가기 버튼과 같은 스타일(반투명 원 + 아이콘, `Color.peekpopSurface.opacity(0.6)`)을 그대로 가져다 씀.

## Primary 버튼 좌우 여백 통일 (디자인 리뷰, 2026-08-29)
메인 화면 "사진 선택하기" 버튼의 48pt 여백이 왜 그 값인지 질문을 받았는데, 실은 의도적 결정이 아니라 초기 구현 때 대충 넣은 값이었다. 화면마다 24(결과)/32(에러)/48(메인·경계확인)pt로 제각각이라 화면별 CTA의 시각적 존재감이 달랐던 것도 같이 발견 — 전부 24pt로 통일했다.

## 기본 경계 사각형(defaultRect) 비율 계산 실수 수정 (2026-08-29)
"세로로 너무 길다"는 지적에 처음엔 halfH를 0.4→0.33으로 줄이고 "비율이 1:1.6→1:1.3으로 완화됐다"고 안내했는데, 이건 계산 실수였다 — `halfW`는 컨테이너 **가로** 기준 프랙션, `halfH`는 컨테이너 **세로** 기준 프랙션이라 서로 다른 축인데, 두 프랙션 숫자를 그대로 비교해서 마치 정사각형 컨테이너인 것처럼 착각했다. 실제로는 세로로 긴 폰 화면(iPhone 기준 약 393x852pt) 위에 그려지므로 실제 화면비는 `(halfW*containerWidth):(halfH*containerHeight)`로 계산해야 하고, 1차 수정 후에도 실제 시각적 비율은 여전히 약 1:2.9로 거의 안 줄어든 상태였다. halfH를 0.15로 다시 낮춰 실제 화면비가 인물 사진에 가까운 ~4:5가 되도록 재계산했다. `ScreenQuadTests.test_defaultRect_isCenteredAndPortrait`도 같은 실수(프랙션을 그대로 비교)를 하고 있어서, 대표 컨테이너 크기(393x852)에 대입해 실제 포인트 값으로 비교하도록 같이 고쳤다.

## 자동화 테스트: 핵심 로직만, UI 테스트 없음
"간결하고 빠르게" 원칙. 화면 흐름 검증은 실기기 수동 QA로 대체한다. 테스트도 실제 샘플 이미지로 돌릴 것이므로 Vision을 mock할 이유가 없어 서비스 타입에 프로토콜 추상화를 두지 않는다.

## 이미지 방향 처리 주의
macOS 스파이크 중 `NSImage.cgImage(forProposedRect:)`가 일부 파일에서 상하 반전된 이미지를 반환하는 버그를 겪었다 (EXIF 메타데이터 문제 아님, 로더 자체의 비일관성). `CGImageSourceCreateImageAtIndex` 직접 디코드로 해결. iOS 구현에서 `UIImage` 자체는 방향을 안정적으로 처리하지만, 원본 픽셀 버퍼를 직접 다루는 합성 코드에서는 이미지 방향을 항상 명시적으로 검증할 것.

## Info.plist / Privacy Manifest
- `NSCameraUsageDescription`: "폰 화면에 보이는 사진을 촬영하기 위해 카메라 접근이 필요해요" — 2번 화면 카메라 선택 시 트리거.
- `NSPhotoLibraryAddUsageDescription`: "완성된 사진을 앨범에 저장하기 위해 접근이 필요해요" — 7번 화면 "저장" 탭 시 트리거.
- 앨범에서 사진을 "고르는" 동작(`PHPickerViewController`)은 권한 자체가 불필요.
- `@AppStorage` 사용으로 Privacy Manifest(`PrivacyInfo.xcprivacy`)에 required-reason API 선언이 필요하다 (사유: "기기 내 앱 자체 데이터 저장 목적" — Xcode 기본 템플릿으로 처리, 추적/분석 목적 아님).

## VNGenerateForegroundInstanceMaskRequest는 iOS 시뮬레이터에서 동작하지 않음
구현 중(Phase 4) 실사진 유닛 테스트가 iOS 시뮬레이터에서 전부 "Could not create inference context"(Vision 에러코드 9)로 실패했다. 코드 버그가 아니다 — 동일 크롭 좌표를 macOS 호스트(`CGImageSourceCreateImageAtIndex` 직접 디코드)에서 돌리면 4장 전부 정상적으로 마스크가 생성됐고(커버리지 71~96%), 시뮬레이터 재부팅 후에도 동일하게 재현돼 플레이키가 아니다. Neural Engine 추론이 필요한 이 요청 자체가 시뮬레이터 런타임에서 지원되지 않는 것으로 판단된다. → 이 API를 쓰는 유닛 테스트는 `#if targetEnvironment(simulator)`로 감지해 `XCTSkip`으로 건너뛰고, 실제 검증은 실기기에서 한다(phase 11 실기기 QA). `PhoneFrameDetector`(`VNDetectRectanglesRequest`)는 시뮬레이터에서도 정상 동작해 이 제약이 없다 — Neural Engine을 쓰는 요청에만 해당.

참고로 macOS 호스트에서 나온 커버리지(71~96%)가 최초 스파이크 때의 값(25~56%)보다 높게 나왔다 — 크롭 프레이밍 차이일 가능성이 있어 실기기 QA 때 함께 눈으로 확인할 것.

## 합성 배치 튜닝: 실기기 QA 피드백 반영, 두 단계
**1차 (고정 상수 조정)**: Phase 11 실기기 QA에서 확대 배율(1.3)이 너무 작고, 배치 비율도 원래 코드가 `insideFraction`(0.42)을 컷아웃 아래쪽 변 기준 "아래로 튀어나오는 양"으로 잘못 다루고 있어서(실제로는 42%만 화면 밖으로 나가고 58%가 화면 위로 다시 겹쳐 그려짐 — 이름과 반대 동작) "튀어나온다"기보다 "화면 위에 살짝 얹힌" 것처럼 보인다는 걸 확인. `popOutScale` 1.3→1.6, `belowEdgeFraction`(개명) 0.42→0.65로 1차 조정.

**2차 (사용자가 수동 조정 UI를 요청했으나 tech-critic-lead가 거부, 대신 알고리즘 개선)**: 사용자가 "피사체 크기·위치를 직접 조정하는 UI"를 요청했지만, tech-critic-lead가 "더 싼 대안(알고리즘 튜닝)을 시도 안 했다"는 근거로 거부했다. 실제로 원인을 다시 보니: 고정 배율(`popOutScale`)이 **컷아웃의 원본 픽셀 크기**를 기준으로 곱해지고 있었는데, 이 픽셀 크기는 사진 해상도·Vision이 얼마나 타이트하게 크롭했는지에 따라 사진마다 들쭉날쭉해서, 같은 배율이어도 "폰 대비 얼마나 커 보이는지"가 사진마다 달라지는 게 진짜 문제였다. → **`targetWidthRatio`(1.15)로 전환**: 컷아웃 픽셀 크기가 아니라 **사용자가 지정한 화면 사각형(quad)의 실제 폭**을 기준으로 목표 폭을 정하고(화면 폭의 1.15배), 거기 맞춰 스케일을 역산한다. 이러면 사진 해상도나 크롭 타이트함과 무관하게 "폰 화면보다 얼마나 커 보이는지"가 항상 일정해진다. `PopOutCompositor.swift` 참고. 유닛 테스트는 이 상수/로직 변경과 무관해(스모크·회전각만 검증) 그대로 통과.

## 미해결 / 다음 버전 과제
- "마스크가 그럴싸함" 판정 임계값(커버리지 %, 화면 경계와의 겹침 정도)은 구현 중 튜닝 필요.
- 배치는 상수 조정 + quad-상대 동적 스케일링까지 했지만, 실제 타겟 고객 노출 전까지는 "충분히 자연스러운가"를 더 검증할 필요가 있다 — 그래도 부족하면 자유 제스처보다 "프리셋 2~3개 중 탭 선택"이 더 싼 다음 단계 (tech-critic-lead 가이드).
- 앱 아이콘/브랜딩: 어두운 둥근 사각형(폰) + 경계를 넘는 밝은 색 블롭, 단순 도형 위주로 — 이 문서 체계 밖의 별도 작업.
